# 准备项目面试回答

## 核心目标

把项目材料转化为三层产物：

1. **记忆框架**：提示回答顺序，并包含足以唤起记忆的具体要点。
2. **面试回答**：从面试官的问题出发，给出可直接说出口的完整回答。
3. **可能追问**：先判断被追问概率，再决定是否提示以及展开深度。

始终优先保证事实准确、职责清晰、逻辑直接、指标可归因和表达自然。

## 隐私边界

- 只读取用户明确提供或授权访问的材料。
- 将内容保存或分享至公开位置前，替换个人姓名、联系方式、账号标识、内部绝对路径、凭据和访问令牌；绝不复述密钥原文。
- 不把真实简历、项目资料、生成回答或运行日志复制到 Skill 目录或公开仓库。公开示例使用合成数据并明确标注。

## 证据与边界

开始写作前，先整理证据，按以下优先级处理冲突：

1. 用户在当前对话中的明确确认或修正；
2. 用户声明已经确定的简历表述；
3. 项目原始材料、PRD、配置、评测和实验文档；
4. 复盘文档与相关参考资料；
5. 基于上下文的合理推测。

遵守以下规则：

- 不读取用户明确排除的材料。
- 用户声明简历已经确定时，把简历作为事实边界，不擅自改写简历。
- 将内容区分为【用户确认】【资料事实】【复盘判断】【推测】【待确认】【待补案例】。
- 不编造模型对比得分、实验结果、用户研究结论、冲突案例或个人职责。
- 同一指标要区分业务终局、项目先导、个人模块、过程诊断和质量护栏。
- 发现材料矛盾时，先指出矛盾与影响，再依据用户确认统一口径。

## 工作流程

### 1. 判断题目真正考什么

先识别面试官希望验证的核心能力：

- 项目背景题：判断用户问题、业务价值和个人贡献。
- 技术选择题：判断目标、候选方案、比较维度、取舍和决策。
- 方法题：判断拆解方式、执行过程、质量控制和结果。
- 指标题：判断指标分层、计算口径、实验归因和护栏。
- 协作或冲突题：判断具体情境、各方约束、决策标准、行动和结果。
- 反思题：判断真实缺陷、形成原因、影响和重做方案。

围绕当前问题组织回答。用户为了纠正歧义补充的信息用于校正事实与逻辑，不自动成为主回答的开场或重点。

### 2. 设计题目专属记忆框架

将“背景或目标—判断与行动—结果或边界”作为内部完整性检查，不直接把“是什么、为什么、怎么做、结果”写成固定标签。

为每道题设计 4—5 个题目专属步骤，每一步同时包含：

- 一个短标签，说明这一段承担的逻辑作用；
- 一句简短的具体要点，足以让用户据此复述。

框架应比主回答短很多，同时避免只剩抽象关键词。

示例：模型选型题使用：

```markdown
> **记忆框架**
>
> - **选型目标：** 说明不同任务分别优先保障什么。
> - **候选方案：** 点出参与比较的模型及各自适用特点。
> - **比较维度：** 同一批 Case 先比质量，过线后再比时延和成本。
> - **最终决策：** 说明选择原则、最终配置和资料边界。
```

其他常用逻辑：

- 架构选择：`架构目标—候选架构—核心取舍—最终方案—代价与效果`。
- 工作流：`触发—上下文—核心处理—状态回写—输出与承接`。
- 项目介绍：`背景痛点—项目目标—个人职责—核心行动—结果价值`。
- 冲突处理：`具体场景—双方约束—共同标准—方案调整—结果反思`。
- 指标判断：`业务目标—核心指标—诊断指标—实验归因—质量护栏`。

### 3. 写面试主回答

先给出一版面试现场可直接复述的回答，再放补充解释。

主回答遵循以下要求：

- 前一两句直接回答题目，避免以防守性澄清、资料缺失或次要争议开场。
- 按记忆框架的顺序展开，每一步形成自然因果。
- 明确“我负责什么、我做了什么”，区分个人工作、参与工作和团队工作。
- 技术或产品选择要说清候选方案、各自特点、比较维度和最终取舍。
- 结果优先使用已确认的量化数据，并说明比较对象和口径。
- 资料不支持的细节放在回答后的资料边界中，不补造数字。
- 使用自然、口语化、可复述的中文，避免把复盘文档原句机械搬入口语回答。
- 控制主回答的重点。技术参数、边界解释和防御性论证仅在直接回答题目所必需时出现。

### 4. 判断是否需要提示可能追问

用户没有主动提出追问时，先判断是否真的存在较高的被追问概率。

以下情况通常属于高概率追问：

- 主回答包含“最终选择了 A”，面试官很可能继续问“为什么不用 B”。
- 使用了关键指标或提升数据，但计算口径、实验组或归因方式尚未展开。
- 声称负责架构、Prompt、评测或模型选型，但缺少具体方法和个人决策。
- 回答依赖明显的技术细节，如 Memory、RAG、工作流、幻觉治理或模型参数。
- 主回答存在自然暴露的限制、失败、代价或未闭环结果。
- 项目是 0—1，证据主要来自离线评测，面试官可能追问上线验证方式。
- 资料之间存在容易被面试官发现的口径差异。

以下情况通常无需主动增加追问：

- 与当前题目关系弱的通用知识题。
- 仅因为“面试官也许会问”而罗列的低概率问题。
- 正文已经充分回答、继续展开只会重复的内容。

若存在高概率追问，只提示 1—3 个问题，并给一行回答方向。若没有高概率追问，省略该部分。

```markdown
### 可能追问

- **为什么采用双 Agent？** 从任务差异、可控性和额外调用成本三方面回答。
```

### 5. 展开用户主动提出的追问

用户主动提出某个追问、质疑或技术歧义时，按照模型选型题 1.1 的详细程度展开：

1. 先修正主回答中受影响的事实或逻辑；
2. 给追问本身设计含具体要点的记忆框架；
3. 写一版可直接复述的追问回答；
4. 按需补充候选方案、任务复杂度、评测方法、参数含义、时序或例子；
5. 标明资料事实与资料边界；
6. 将防守性说明放到对应追问下，不让它抢占主问题的回答重点。

例如，用户指出“这是 0—1 项目，选型前不能比较线上指标”时：

- 修正选型流程为离线 Case、测试环境压测、确定模型、接入产品、小流量灰度；
- 主问题仍从选型目标和候选方案开始；
- “为什么没有线上指标、灰度处于哪个阶段”单列为追问，不作为主回答开头。

## 默认输出结构

```markdown
## [题号] [问题]

> **记忆框架**
>
> - **题目专属步骤一：** 一句具体要点。
> - **题目专属步骤二：** 一句具体要点。
> - **题目专属步骤三：** 一句具体要点。
> - **题目专属步骤四：** 一句具体要点。

### 面试回答

> 可直接复述的主回答。

【资料边界】仅在存在资料缺口时添加。

### 可能追问

- 仅列高概率问题，并给一行回答方向。
```

若用户主动提出某个追问，在其下增加完整的记忆框架、面试回答和必要的细节展开。

## 修改与复盘规则

收到用户批注时，逐条判断批注属于哪一类：

- **事实修正**：更新所有受影响的框架、主回答、追问和指标口径。
- **回答视角修正**：重新从面试官的问题出发组织主回答。
- **重点调整**：降低次要信息权重，把关键价值与个人职责前置。
- **未来优化**：放入项目缺陷或重做方案，不回写成已上线能力。
- **资料边界**：保留推测或待确认标记，不将其写成事实。

修改后检查相同事实是否在不同题目中保持一致，尤其检查职责、实验分组、提升数据、业务指标、模型配置和已上线/未来优化的边界。

## 交付前检查

- 记忆框架是否使用题目专属标签，并包含简短具体要点？
- 主回答是否在前一两句正面回答了问题？
- 用户补充的歧义是否只影响相关事实和追问，没有抢占主回答？
- 个人负责、参与和团队负责是否清晰区分？
- 指标是否说明层级、比较对象、口径和当前验证状态？
- 技术选择是否包含候选方案、特点、比较维度、取舍和决策？
- 推测、待确认和待补案例是否明确标注？
- 是否只提示真正高概率的追问？
- 用户主动提出的追问是否达到详细展开标准？
- 不同题目之间的职责、数据和项目事实是否一致？
