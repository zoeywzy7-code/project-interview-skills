# 项目面试叙事框架

## 目标

将项目材料整理为一条可解释、可验证、可追问的叙事链：

`业务目标与用户价值 → 现状问题 → 解决策略 → 数据验证 → 后续迭代`

保留用户提供的事实和表达重点。不得编造经历、决策、数据或结果。信息不足时标注“待补充”，并说明缺失信息影响哪个判断。

## 隐私边界

- 只读取用户明确提供或授权访问的材料。
- 将内容保存或分享至公开位置前，替换个人姓名、联系方式、账号标识、内部绝对路径、凭据和访问令牌；绝不复述密钥原文。
- 不把真实项目材料、生成结果或运行日志复制到 Skill 目录或公开仓库。公开示例使用合成数据并明确标注。

## 默认交付

除非用户指定其他形式，直接在对话中输出：

1. 一句话项目主线；
2. 时间轴与项目定位；
3. Why、现状问题、策略、验证、迭代五部分；
4. 问题—策略—指标映射表；
5. 关键待补信息。

用户要求“面试现场可直接说”时，再将框架改写为口语化回答。用户只要求框架时，保留结构化表达，不擅自扩展成长篇逐字稿或文档。

## 工作流程

### 1. 盘点材料

提取并区分：

- 已知事实：用户明确提供的背景、行动、数据和结论；
- 合理归纳：可由多条事实直接归纳的判断；
- 待补信息：无法从材料确认、但会影响叙事闭环的内容。

优先继续整理已有材料。只有缺失信息会实质改变项目主线时，才向用户提一个最关键的问题；其余缺口放入“待补信息”。

### 2. 用时间轴定位项目

先还原：

`既有业务与团队能力 → 项目启动 → 当前阶段 → P0上线 → 数据验证 → 后续阶段`

明确：

- 当时的业务阶段与背景；
- 项目承接的业务 OKR 或核心指标；
- 用户本人负责的阶段、职责和边界；
- 项目对小团队与大团队的价值；
- P0、验证和迭代发生的关键节点。

没有明确日期时使用阶段名称，不推测日期。

### 3. 整理 Why

同时回答对内与对外两个 Why。

对内说明：

- 为什么在当时做；
- 服务于什么业务目标或 OKR；
- 对小团队有什么收益；
- 对大团队或公司有什么价值。

对外说明：

- 核心用户是谁；
- 用户在什么场景下完成什么任务；
- 原有方式存在什么痛点；
- 项目为用户带来什么可感知收益；
- 用户持续使用或付费的理由是什么。

用一句话收束需求定义：

`为[用户]在[场景]下解决[问题]，创造[用户价值]，并支撑[业务目标]。`

### 4. 收敛现状问题

优先收敛为三个核心问题。问题数量应服从材料，不能为凑数拆分或合并。

每个问题使用同一结构：

`问题表现 → 证据 → 根因判断 → 用户影响 → 业务影响`

区分现象与根因。例如“留存低”是现象；价值感知弱、结果不稳定或场景低频可能是根因。只有材料支持时才确认根因，否则标为待验证假设。

按用户价值、业务影响、紧迫性和可验证性解释问题优先级。

### 5. 形成策略

先盘点团队可用条件：

- 技术、模型、数据、产品、运营和渠道能力；
- 可迁移的历史积累；
- 人力、时间、技术和组织约束；
- 团队优势与短板。

再拆分短期和长期策略。

短期策略用于 P0 验证，必须与核心问题一一对应。每项说明：

`目标问题（要解决什么，含关键约束） → 策略判断（为什么这样解决） → 关键动作 → 用户本人贡献 → 预期指标`

将目标问题定义为当前策略需要解决的具体命题，可吸收由现状问题延伸出的关键困难、边界与约束；根据项目材料判断即可，不限定问题类型或项目阶段。

将策略判断写成从目标问题到方案的推理结论。结合根因、团队能力、限制条件、风险与取舍，解释为什么选择这条路径；避免用功能或动作清单代替策略判断。

长期策略用于解决跨问题的系统性原因，可以同时覆盖多个问题。说明长期方向即可，避免抢占 P0 落地内容的篇幅。

解释策略优先级时，综合判断用户影响、业务贡献、团队能力、成本、周期和验证价值。

### 6. 组织验证

将指标分为三层：

- 能力或产品指标：准确率、任务完成率、采纳率、响应时间、人工修改率等；
- 用户价值指标：激活率、留存、使用频次、满意度、节省时间或成本等；
- 业务价值指标：渗透率、转化率、付费、收入、成本或 OKR 完成度等。

每项结果必须回连一个问题和一项策略。优先采用：

`基线 → 行动 → 结果 → 变化幅度 → 用户价值 → 业务价值`

补充验证方法，如上线前后对比、A/B 实验、灰度测试、同期对照、分群分析或用户访谈。只有材料证明因果关系时才使用因果表述；其余情况使用“与……一致”“支持……判断”或“可能相关”。

如结果未达预期，保留真实结果，并说明它推翻或修正了什么假设。

### 7. 推导迭代

从验证结果直接推导下一阶段：

- 已验证有效：扩大覆盖范围或规模化；
- 部分有效：寻找剩余限制因素；
- 未达预期：修正假设与方案；
- 出现新问题：重新排序优先级。

按需要使用阶段节奏：

- P0：验证核心需求与价值；
- P1：优化体验、稳定效果与留存；
- P2：规模化、商业化或平台化。

说明下一阶段要解决的问题、计划采取的动作、衡量指标，以及对用户和团队的长期收益。让迭代回扣最初的 Why。

### 8. 检查闭环

输出前逐项检查：

- Why 中的业务目标是否在验证部分得到回应；
- 每个核心问题是否有证据或明确的待验证假设；
- 每项短期策略是否对应一个核心问题；
- 每项策略判断是否解释了关键困难、约束和取舍如何影响方案选择；
- 策略是否符合团队能力、资源和项目阶段；
- 每个结果是否说明了用户价值与业务价值；
- 后续迭代是否由验证结果自然推导；
- 用户本人的判断、动作和贡献是否清楚。

## 表达要求

- 先给结论，再给证据和过程。
- 使用具体动作、决策与数据，减少空泛的方法论描述。
- 明确区分团队成果和用户本人贡献。
- 保留失败、权衡与修正，它们能够体现判断力。
- 控制主线数量，避免并列过多问题与策略。
- 不使用虚构占位数据冒充真实结果；需要示例时显式标注“示例”。
